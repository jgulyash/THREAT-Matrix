# Migrating from schema 2.1 to schema 3.0

**Status: draft on branch `v3-design`. The release has not been announced and no date has been set.** Schema 2.1.0 with content 1.7.0 remains the published version on `main` until the 3.0.0 release is announced and tagged under [VERSIONING.md](../VERSIONING.md).

**Baseline.** This guide is written against the published document: `docs/data/framework.json` on `origin/main` (content 1.7.0, schema 2.1.0). Every count and every test result below was produced on that document on 2026-11-15. An earlier draft of this guide was measured against an unpublished working copy and missed the largest change. This one replaces it.

**Who needs this.** Anyone who holds a copy or fork of the published `framework.json`, or whose code reads it. If you only read the published file, you can download the 3.0.0 files instead of migrating a copy, but your code still has to change where the sections below say so.

## What changed, in one paragraph

Schema 3.0.0 turns `framework.json` into a vocabulary with no scores. Every score, the scoring rubric, the case-level scoring rules, and the per-tactic priority moved to a separate experimental file, `docs/data/scoring-overlay.json`, with renamed fields. The countermeasure relation `compensates_for` was split in two. A lifecycle contract was added. Many patterns and enums were tightened. The default case record is new and score-free; the old scored record survives only as an experimental format beside the overlay. The content version that ships with schema 3.0.0 is 2.0.0.

No identifier was renamed, renumbered, or removed. A manifest generated from the published 1.7.0 document compares clean against the 2.0.0 manifest.

## Breaking changes

| | Change | Breaks |
|---|---|---|
| A | `schema_version` is `3.0.0` | Every 2.x document, and any code that pins the version |
| B | `evidence_basis` values renamed | 122 tactics in the published document; code that matches the old values |
| C | `compensates_for` narrowed; indicator targets moved to `mitigates` | 476 references on 283 countermeasures; code that reads `compensates_for` for indicator coverage |
| D | Scores, rubric, case-level rules, and tactic priority moved to the overlay, with renames | All 828 indicators, 159 tactics, and two root blocks; any code that reads a score from `framework.json` |
| E | Root `operations` removed | The published document, which carries an empty `operations` array |
| F | `matrices.<name>.maturity` required | Every 2.x document |
| G | Lifecycle contract; reserved actor-profile stubs | Code that assumes every `actor_profiles` entry has a `name` |
| H | Patterns, enums, and URL schemes tightened; several optional structures now complete-or-absent | Forks with non-conforming values; 4 missing fields in the published document |
| I | Indicator field `primary_objective_evidence_tier` removed | Documents that set it (the published document does not) |
| J | Four bibliography `type` values removed | 1 entry in the published document |
| K | `license` must be `MIT` | Forks that changed the value |
| L | Case record split: old definitions moved to the overlay schema and renamed; new score-free record | Stored `conditioned_assessment` records; code that validates records against `framework.schema.json` |
| M | Content rules new in the validator | 72 `phase_relevance` values and 12 `axis_confidence` labels in the published document |

Unchanged: the schema `$id` (`https://jgulyash.github.io/THREAT-Matrix/data/framework.schema.json`), which carries no version. The schema file records its version in `x-schema-version`.

---

### A. schema_version

**What.** `schema_version` must match `3.x.y`; the validator pins exactly `3.0.0` (check V24). `version` must be a SemVer 2.0.0 string.

**Why.** A document declares the schema it was written for.

**Remediation.** Set `schema_version` to `3.0.0`. Update any check in your code that pins `2.1.0`.

```jsonc
// 2.1                          // 3.0
"schema_version": "2.1.0"       "schema_version": "3.0.0"
```

### B. evidence_basis value rename

**What.** The tactic field keeps its name and stays required. Three of its four values are renamed.

| 2.1 value | 3.0 value | Tactics in the published document |
|---|---|---:|
| `operational_primary` | `practice_led` | 10 |
| `hybrid` | `practice_and_literature` | 111 |
| `literature_primary` | `literature_led` | 1 |
| `literature_only` | `literature_only` | 39, unchanged |

**Why.** The old names read as claims about non-public operational data. The field states how a tactic was written, and every object cites public sources only whatever the value.

**Remediation.** Apply the mapping. It is one to one. Update every literal in your code that matches, filters, or labels the value.

```jsonc
// 2.1                                    // 3.0
{ "id": "TM0103",                         { "id": "TM0103",
  "evidence_basis": "operational_primary"   "evidence_basis": "practice_led"
}                                         }
```

### C. The relation split: compensates_for and mitigates

**What.** In 2.1.0 a countermeasure's `compensates_for` array could hold countermeasure identifiers and indicator identifiers (pattern `^(CM|IND)-...`). In 3.0.0:

- `compensates_for` holds countermeasure identifiers only. It means: this countermeasure covers for the absence or failure of that one. An indicator identifier here is rejected by the schema and by the validator (check V07).
- A new optional array, `mitigates`, holds the indicator targets. Each entry is an edge object with exactly two keys: `indicator` (an indicator identifier) and `function` (`prevent`, `detect`, `deny`, or `unreviewed`).

The published document has 836 `compensates_for` entries: 360 countermeasure identifiers, which stay, and 476 indicator identifiers on 283 countermeasures, which must move.

**Why.** One field carried two different relations. A consumer could not tell redundancy between controls from coverage of a behavior.

**Remediation.** For each countermeasure, move every `IND-` entry out of `compensates_for` into `mitigates` as `{"indicator": "<id>", "function": "unreviewed"}`. Keep `compensates_for` even when it ends up empty. If your code read `compensates_for` to find the indicators a countermeasure covers, read `mitigates` instead. Do not treat a migrated edge as typed: `unreviewed` says only that a link exists. In the 2.0.0 data all 483 edges are `unreviewed`.

```jsonc
// 2.1
{ "id": "CM-F0102-03",
  "compensates_for": ["IND-F0102-02", "IND-F0102-03", "CM-0103-01"] }

// 3.0
{ "id": "CM-F0102-03",
  "compensates_for": ["CM-0103-01"],
  "mitigates": [
    { "indicator": "IND-F0102-02", "function": "unreviewed" },
    { "indicator": "IND-F0102-03", "function": "unreviewed" }
  ] }
```

### D. Scores moved to the experimental overlay

**What.** `framework.json` no longer holds any score. These fields are not allowed in a 3.0.0 vocabulary document (every object is closed, and validator check V29 names them), and each has a new home in `docs/data/scoring-overlay.json`:

| 2.1.0 location in `framework.json` | 3.0.0 location in `scoring-overlay.json` |
|---|---|
| indicator `escalation_axes` | `indicator_scores[<indicator id>].axes` |
| indicator `escalation_weight` | `indicator_scores[<indicator id>].type_weight` |
| indicator `severity_band` | `indicator_scores[<indicator id>].type_band` |
| indicator `severity_floor` | `indicator_scores[<indicator id>].type_band_floor` |
| indicator `axis_confidence` | `indicator_scores[<indicator id>].axis_confidence` |
| tactic `assessment_guidance.escalation_priority` | `tactic_priorities[<tactic id>]` |
| root `escalation_rubric` | `rubric` (with `severity_thresholds` renamed `type_band_thresholds` and `severity_floor_rule` renamed `type_band_floor_rule`) |
| root `instance_conditioning` | `instance_conditioning` |

The overlay has its own schema (`docs/data/scoring-overlay.schema.json`) and its own version (0.1.0). Its header declares `status: experimental`, `normative: false`, `validation_status: unvalidated`, `scope: type_level`, and `not_a_risk_score: true`, and carries a notice paragraph. Its `indicator_scores` keys must equal the vocabulary's indicator identifiers exactly, and `applies_to_framework_version` must equal the vocabulary's `version`.

The six remaining parts of `assessment_guidance` (credibility, capability, intent, opportunity, `false_positive_context`, `threshold_guidance`) stay in the vocabulary.

**Why.** The values are authored estimates for classes of behavior. They have not been validated against outcomes or checked by independent reviewers, and inside the vocabulary they read as properties of the behavior and, by extension, of a person. They are now a separate, opt-in, non-normative file that a consumer has to choose to load. See [METHODOLOGY.md](../METHODOLOGY.md#limitations-and-intended-use).

**Remediation.** Remove the fields from the vocabulary document and, if you want to keep the values, write them to an overlay file in the shape above. If your code read a score from `framework.json`, decide first whether it should read one at all. If it should, load the overlay explicitly, show its notice, check `applies_to_framework_version`, and join by indicator identifier. Do not show a band against a person or place one in a case record.

```jsonc
// 2.1: framework.json, indicator IND-0101-01
{ "id": "IND-0101-01",
  "escalation_axes": { "impact_potential": 5.0, "blast_radius_potential": 2.5,
                       "recoverability_inverse": 6.5, "detectability": 5.0 },
  "escalation_weight": 4.49,
  "severity_band": "medium",
  "axis_confidence": { "impact_potential": "inferred", "blast_radius_potential": "established",
                       "recoverability_inverse": "inferred", "detectability": "inferred" } }

// 3.0: framework.json, indicator IND-0101-01 has none of those fields.
// 3.0: scoring-overlay.json
{ "indicator_scores": {
    "IND-0101-01": {
      "axes": { "impact_potential": 5.0, "blast_radius_potential": 2.5,
                "recoverability_inverse": 6.5, "detectability": 5.0 },
      "type_weight": 4.49,
      "type_band": "medium",
      "axis_confidence": { "impact_potential": "inferred", "blast_radius_potential": "established",
                           "recoverability_inverse": "inferred", "detectability": "inferred" } } },
  "tactic_priorities": { "TM0101": "Priority" } }
```

Two rules are stricter in the overlay than they were in 2.1.0. The stored weight must be within 0.005 of the value computed from the axes (it was 0.06), and the band is read from the stored two-decimal weight.

### E. Root operations removed

**What.** The root object is closed and no longer has an `operations` property. The published document carries `"operations": []`.

**Why.** It was an empty placeholder for a feature that does not exist.

**Remediation.** Delete the key. Stop reading it.

```jsonc
// 2.1                          // 3.0
{ "operations": [], ... }       { ... }
```

### F. Matrix maturity required

**What.** Each of the four matrix objects must carry `maturity`, with the value `core` or `draft`, beside `scope`. In the 2.0.0 data, `person` and `facility` are `core`; `organization` and `infrastructure` are `draft`.

**Why.** The four matrices are not equally mature, and a consumer needs to be able to tell from the data.

**Remediation.** Add the field. Show it wherever you show a matrix. Treat draft content accordingly.

```jsonc
// 2.1                                   // 3.0
"organization": { "scope": "...",        "organization": { "scope": "...",
                  "tactics": [ ... ] }                     "maturity": "draft",
                                                           "tactics": [ ... ] }
```

### G. Lifecycle contract

**What.** Tactics, indicators, countermeasures, response protocols, and actor profiles gain optional lifecycle fields: `lifecycle_state` (`active`, `deprecated`, `superseded`; and `reserved` on actor profiles only), `deprecated_in`, `deprecation_reason`, and `superseded_by`. Actor profiles also gain `reserved_reason`. The rules, enforced by schema and validator (check V26):

- absent `lifecycle_state` means `active`, and an active object carries none of the other lifecycle fields;
- `deprecated` requires `deprecated_in` and `deprecation_reason`;
- `superseded` requires those and `superseded_by`, which must name an active object in the same namespace, not itself, with no cycle;
- only an actor profile may be `reserved`, and a reserved profile carries only `id`, `lifecycle_state`, and `reserved_reason`.

The 2.0.0 document has 34 entries in `actor_profiles`: 32 profiles and 2 reserved stubs (`AP022`, `AP027`). The published 1.7.0 document has 32 entries and no stubs. A per-release ID manifest (`docs/data/id-manifest.json`) is new; see [IDENTIFIERS.md](../IDENTIFIERS.md).

**Why.** The deprecation policy has required lifecycle states since V1.1, but the closed 2.x schema could not express them. The full contract is in [DEPRECATION.md](../DEPRECATION.md).

**Remediation.** For a copy of the published document, nothing is required: no lifecycle field is mandatory, and the stubs are optional. For code: treat a missing `lifecycle_state` as `active`; skip reserved actor profiles before reading `name`, `category`, or any other profile field; mark deprecated and superseded objects where you show them.

```jsonc
// 2.1: actor_profiles has no entry for AP022.
// 3.0: actor_profiles includes
{ "id": "AP022",
  "lifecycle_state": "reserved",
  "reserved_reason": "Former-insider behavior is modeled via the employment_status modifier on actor_associations rather than as a separate profile (V1.0 design review)." }
```

### H. Tightened patterns, enums, and structures

**What.** Every rule below is new in 3.0.0. The published document satisfies all of them except the one marked.

| Rule | Where | Detail |
|---|---|---|
| Identifier grammar | tactic, indicator, countermeasure, response protocol, and actor profile identifiers and every reference to one | Phase digits must be `01` to `04`; sequence numbers may not be `00`. For example the indicator pattern changed from `^IND-[FOI]?[0-9]{4}-[0-9]{2}$` to `^IND-[FOI]?0[1-4](0[1-9]\|[1-9][0-9])-(0[1-9]\|[1-9][0-9])$`. `related_tactics` entries must be tactic identifiers. |
| Bibliography keys | `bibliography` property names and every `source_refs` entry | `^[A-Z][A-Z0-9]*(-[A-Z0-9]+)+$` |
| Bibliography URL | `bibliography.<key>.url` | `null`, or an `http` or `https` URL with no whitespace. Every other scheme is rejected. |
| Bibliography DOI and date | `doi`, `date` | `doi` is `null` or a bare DOI (`10.NNNN/suffix`). `date` is `YYYY`, `YYYY-MM`, `YYYY-MM-DD`, `YYYY-YYYY`, or `n.d.` with an optional access date. |
| Text | every free-text field | Non-empty, with no leading or trailing whitespace |
| `phase_name` | tactic | One of `Target Development`, `Mobilization`, `Execution`, `Aftermath` |
| Actor-profile enums | `category`, `category_label`, `awareness`, `direction`, `access_relationship`, `phase_compression_risk`, `actor_level` | Fixed value lists, taken from the values in use |
| `assessment_guidance` | tactic | Optional, but when present all six parts are required, and each part's own fields are required. **The published document fails this on 2 tactics** (see the test below). |
| `informs_axes` | indicator | Optional, but when present all six axes are required |
| `indicators` | tactic | At least one |
| `actor_associations` | tactic | No repeated entry |
| `v2_tactic_associations` | actor profile | No longer required. Items, if any, must be `{tactic_id, relevance}` objects. |
| `phase_mappings` | root | Exactly the four phase keys |
| `detection_mesh` | root | Exactly the five named axes; `schema_links` complete |
| `actor_profiles`, `bibliography` | root | Not empty |

**Why.** The 2.1.0 schema accepted malformed identifiers, script-scheme URLs, empty text, and half-filled structures.

**Remediation.** For a copy of the published document: write the four missing guidance fields (section "Test on the published document"). For a fork: correct any value the schema reports. The validator names each failing object.

```jsonc
// accepted by the 2.1 schema                   // required by the 3.0 schema
{ "related_tactics": ["recon"],                 { "related_tactics": ["TM0101"],
  "source_refs": ["ntac mass 2021"] }             "source_refs": ["NTAC-MASS-2021"] }

// bibliography entry
{ "url": "javascript:alert(1)", "doi": "https://doi.org/10.2172/2229613" }   // 2.1 accepted
{ "url": null,                  "doi": "10.2172/2229613" }                   // 3.0 required
```

### I. Indicator field primary_objective_evidence_tier removed

**What.** The optional indicator field `primary_objective_evidence_tier` no longer exists in the vocabulary schema. No indicator in the published document sets it.

**Why.** It annotates an incident, not a class of behavior. It never belonged on an indicator.

**Remediation.** Remove it from any indicator that carries it. A field of the same name remains, as an optional case-level annotation, on the experimental scored record in the overlay schema.

```jsonc
// 2.1 (allowed on an indicator)                          // 3.0
{ "id": "IND-0101-01",                                    { "id": "IND-0101-01" }
  "primary_objective_evidence_tier": "stated" }
```

### J. Bibliography type values removed

**What.** The bibliography `type` enum loses four values: `field_observation`, `practitioner_elicitation`, `partner_attestation`, and `case_composite`. The remaining values are `government_report`, `academic_paper`, `book`, `court_document`, `after_action_review`, `news_investigation`, `incident_database`, `practitioner_guide`, and `standard`.

**Why.** The four removed types described non-public sources. Every object cites public sources only, and the schema now cannot express anything else.

**Remediation.** The published document has one entry with a removed type (`field_observation`), cited from 1,138 `source_refs` arrays. Either remove that entry and every reference to it, giving a public source to any object left with none, or replace it with a public source. In the 2.0.0 data the entry is gone, and the 93 objects that cited nothing else were given public sources (recorded in the CHANGELOG entry for 1.7.1).

```jsonc
// 2.1                                         // 3.0
"SOME-KEY-2020": { "type": "field_observation" }   // not valid; remove or replace with a public source
```

### K. License constant

**What.** `license` must be the string `MIT`. In 2.1.0 it was any string.

**Why.** The value is the license of the published vocabulary, not a free field.

**Remediation.** None for a copy of the published document. A fork that needs a different value needs its own schema.

```jsonc
// 2.1 (accepted)            // 3.0
"license": "none"            "license": "MIT"
```

### L. Case record split

**What.** In 2.1.0, `framework.schema.json` defined two case-level objects: `instance_assessment` (six instance factors) and `conditioned_assessment` (an indicator, its quoted band, the instance, and a priority that may not be below the band). In 3.0.0:

- Both definitions are gone from `framework.schema.json`.
- They live in `docs/data/scoring-overlay.schema.json` as `$defs.instance_assessment` and `$defs.scored_case_record`. The record's field `type_severity_band` is renamed `type_band`. Optional `framework_version` and `overlay_version` are added. The `disposition` list gains `no_threat_identified` and `transient_no_further_action`. This record is experimental, like the overlay it depends on.
- A new **score-free case record** is the default: `docs/data/case-record.schema.json`, record version 1.0.0. It has no band, weight, priority, or score field and its schema is closed. It adds what the old record lacked: the vocabulary version, a case reference, the date, the assessor's role, several observations per record with their sources, protective factors, reassessments in either direction, and a required acknowledgment of the limitations. Its `subject_term` is fixed to `person_of_concern`.

The validator now checks a scored record against the overlay: the indicator must exist, and the quoted `type_band` must equal the overlay's band for that indicator (`--records`, checks V18, V47, V48). In 2.1.0 nothing checked that.

**Why.** A priority that can only rise, tied to a single indicator, with no place for protective factors, is not a sound default for a record about a person.

**Remediation.** A stored 2.1.0 `conditioned_assessment` can be kept as an experimental scored record by renaming `type_severity_band` to `type_band` and validating against `scoring-overlay.schema.json#/$defs/scored_case_record`. It cannot be converted to the score-free record mechanically: that record has to be written, because it asks for information the old one never held. For casework, write new records in the score-free format. Templates and worked cases are in [examples/](../../examples/README.md).

```jsonc
// 2.1: conditioned_assessment (validated against framework.schema.json)
{ "indicator_id": "IND-0101-01",
  "type_severity_band": "medium",
  "instance": { "target_focus": "unknown", "pathway_stage": "unknown", "means_in_hand": "unknown",
                "tempo_trajectory": "unknown", "proximity_access": "unknown",
                "source_credibility": "unknown", "basis": "..." },
  "conditioned_priority": "medium" }

// 3.0, experimental: scored_case_record (validated against scoring-overlay.schema.json)
{ "indicator_id": "IND-0101-01",
  "type_band": "medium",
  "instance": { "target_focus": "unknown", "pathway_stage": "unknown", "means_in_hand": "unknown",
                "tempo_trajectory": "unknown", "proximity_access": "unknown",
                "source_credibility": "unknown", "basis": "..." },
  "conditioned_priority": "medium" }

// 3.0, default: score-free case record (validated against case-record.schema.json)
// See examples/case-record-template.json. It has no band or priority field.
```

### M. Content rules new in the validator

**What.** `scripts/lint/validate.py` now applies rules that a schema cannot express. Two of them fail on the published document after migration:

- **V35.** An indicator's or countermeasure's `phase_relevance` must include its parent tactic's phase. 72 objects in the published document omit it.
- **V20** (with the overlay). Each `axis_confidence` label must equal the label its derivation rule gives. 12 indicators in the published document carry a label that differs.

Others apply to any fork: every bibliography entry must be cited (V36); an actor association must resolve to a profile that is not reserved (V31); `related_tactics` must resolve (V32); no relation may refer to its own object or repeat an entry (V33); a tactic identifier must encode its phase (V34).

**Why.** Each rule was already stated in the documents or implied by the data, and nothing checked it.

**Remediation.** For V35, add the parent tactic's phase to `phase_relevance`, or move the object to the tactic whose phase it describes. For V20, set each label in the overlay to the value printed by `python3 scripts/analysis/derive-axis-confidence.py --print-derived --framework F --overlay O`.

```jsonc
// 2.1 (accepted): an indicator under a phase 1 tactic      // 3.0 (required)
{ "id": "IND-0104-01",                                      { "id": "IND-0104-01",
  "phase_relevance": ["mobilization"] }                       "phase_relevance": ["target_development", "mobilization"] }
```

## The migration tool

`scripts/migrate/2.1-to-3.0.py` performs the shape changes. Its own documentation is [scripts/migrate/README.md](../../scripts/migrate/README.md).

```
python3 scripts/migrate/2.1-to-3.0.py path/to/framework-2.1.json --dry-run

python3 scripts/migrate/2.1-to-3.0.py path/to/framework-2.1.json \
    --out-framework out/framework.json \
    --out-overlay out/scoring-overlay.json \
    --report out/migration-report.json
```

**What it does.** Changes A, B, C, D, E, and F: sets `schema_version`; renames the three `evidence_basis` values; drops root `operations` (saving any content in the report); splits `compensates_for`, turning each indicator reference into a `mitigates` edge with function `unreviewed`; moves every score, the tactic priorities, the rubric, and the case-level rules into an overlay file in the 3.0.0 shape with the renames; and adds `maturity`. It then validates its output against the 3.0.0 schemas, runs `validate.py` on it, and lists everything that still fails, each item with a suggested fix. Exit code 0 means nothing is left; 1 means the outputs were written and manual work is listed; 2 means the input could not be used.

**What it does not do.**

- It does not change content. No behavior text, guidance, citation, or score value is reviewed or edited.
- It does not fix what 3.0.0 rejects for content reasons (changes H, J, and M). It lists those.
- It does not choose a `function` for a `mitigates` edge. Every migrated edge is `unreviewed`.
- It does not edit prose that mentions an old field name. It lists the mentions.
- It does not set the content `version` unless you pass `--content-version`.
- It does not add reserved actor-profile stubs or write an ID manifest.
- It does not migrate case records (change L).
- Moving a score to the overlay does not validate it. The overlay it writes is labelled experimental, non-normative, and unvalidated.

## Test on the published document

Run on 2026-11-15 with Python 3.14.0 and `jsonschema` 4.26.0. To reproduce:

```
git show origin/main:docs/data/framework.json > /tmp/framework-2.1.json
python3 scripts/migrate/2.1-to-3.0.py /tmp/framework-2.1.json \
    --out-framework /tmp/out/framework.json \
    --out-overlay /tmp/out/scoring-overlay.json \
    --report /tmp/out/migration-report.json
```

**Before.** The published document has 0 errors against the published 2.1.0 schema and 1,596 errors against the 3.0.0 schema.

**What the tool changed.** 1 `schema_version`. 122 `evidence_basis` values (111, 10, and 1). Root `operations` dropped. 476 indicator references moved to `mitigates` edges on 283 countermeasures; 360 countermeasure references kept. Scores moved for 828 indicators, 43 of them with a floor. 159 tactic priorities moved. The rubric and the case-level rules moved, with 2 key renames. 4 `maturity` values added.

**After.** The overlay has 0 schema errors. The vocabulary has 5 schema errors. `validate.py` on the vocabulary fails 2 checks (the schema check and V35); with the overlay it fails 3 (adding V20). `mesh-refs.py` and `field-parity.py` pass. The tool exits 1 and lists 14 items: 5 schema items, 2 validator items, and 7 groups of prose mentions.

Every remaining failure is a content defect in the published document that 3.0.0 checks and 2.1.0 did not:

| Remaining item | Count | Change | Manual remediation |
|---|---:|---|---|
| A bibliography entry has a `type` that 3.0.0 does not allow | 1 | J | Remove the entry and its references, or replace it with a public source. |
| `TO0212` and `TI0211` lack `assessment_guidance.false_positive_context` and `threshold_guidance` | 4 | H | Write the two fields for each tactic. |
| `phase_relevance` omits the parent tactic's phase (V35) | 72 | M | Add the parent tactic's phase, or move the object. |
| `axis_confidence` label differs from its rule (V20) | 12 | M | Set each label to the rule's value. |
| Text values that still mention an old field name | 7 groups | D | Edit the wording. This is not a validation failure. |

**Completeness of the list.** With those 89 values corrected by hand in a scratch copy (1 type, 4 guidance fields, 72 `phase_relevance` lists, 12 labels), `validate.py --require-schema` reports 35 of 35 checks passing on the vocabulary and 45 of 45 with the overlay, and `mesh-refs.py` and `field-parity.py` pass. So the tool plus the listed manual work takes the published document to a valid 3.0.0 pair. The scratch corrections were placeholders to prove the list is complete; the real corrections are in the 2.0.0 data and are content decisions.

A fuller record of this run and of the gate results on the 2.0.0 files is in [3.0.0-validation-report.md](./3.0.0-validation-report.md).
